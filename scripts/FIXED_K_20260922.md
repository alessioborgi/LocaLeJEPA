# Fixed-K campaign (180 runs)

Implements only the first grid row in `ablations_design_2026-09-22.pdf`:
lambda {0.02, 0.05, 0.1, 0.2, 0.3}, K {1, 2, 4, 8, 16, 32},
batch/accumulation {64/4, 256/1}, seeds {42, 43, 44}.
Seeds are a campaign choice; the PDF specifies three seeds but no IDs.
ViT-S/8, Imagenette, 128px, 100 epochs, single GPU, AdamW lr 0.001,
10 warm-up epochs, cosine floor 0.000001, gradient clipping 1.0.

## Launch on diufrd

Transfer this campaign config, launcher, and the modified `src/losses.py` and
`src/models/lejepa_module.py` to your cluster checkout before submitting.
The files are tracked by git (unlike the ignored `slurm/` directory).
From the repository root on the cluster:

```bash
uv sync --extra experiments
mkdir -p logs/slurm
# Configure W&B credentials/project in .env as for existing runs.
# DATA_DIR, if needed, is the parent directory containing imagenette/.
# export DATA_DIR=/your/dataset/root
# export ENV_SETUP=/your/module_setup.sh
DRY_RUN=1 bash scripts/slurm_fixed_k_20260922.sh 0
bash scripts/submit_fixed_k_20260922.sh
```

The submission wrapper creates two disjoint 90-task arrays: B64 requests 40G host
RAM, B256 requests 80G. These provide about 35% headroom over the confirmed
29.0/58.6 GiB MaxRSS of jobs 23514_1/23514_3. This campaign's peaks remain unmeasured.
Each task requests one GPU and 24 hours on partition gpu. By default one task
per array runs at once (two GPUs and up to 120G host RAM in total).
`MAX_CONCURRENT=2 bash scripts/submit_fixed_k_20260922.sh` allows two per array,
four total. Preview without submission using
`DRY_RUN=1 bash scripts/submit_fixed_k_20260922.sh`.
Direct submission of the underlying launcher uses 80G and one concurrent task.
Index order: seed changes fastest, then batch, K, lambda. Index 0 is lambda 0.02,
K1, B64x4, seed42; index 179 is lambda 0.3, K32, B256x1, seed44.
To retry an interrupted task, use `sbatch --array=INDEX --mem=40G scripts/slurm_fixed_k_20260922.sh`
for B64, or `--mem=80G` for B256; last.ckpt
is resumed automatically. Do not run duplicate indices concurrently. Automatic
successor submission is disabled. Use a different exported RUN_PREFIX for a fresh campaign.

## Outputs and reporting

Checkpoints: `checkpoints/<run-name>/{best,last}.ckpt`.
Resolved Hydra config and CSV metrics: `logs/ablations/<run-name>/`.
W&B group: `fixed_k_20260922`. CSV logging is enabled alongside W&B.
On resume CSVLogger creates another version directory; combine those versions
by epoch when reporting, preferring the newest record for repeated epochs.

Use `val/probe_acc` at epoch 99, not best validation accuracy or the best-checkpoint
test score. Test-after-fit is disabled. Average `train/local/effective_clusters_epoch` across
epochs 90 through 99 for K-hat, then aggregate the three seeds (mean and sample
standard deviation). Incomplete runs must remain missing.

Diagnostics use the implementation from `origin/claudio_cluster` at `fea0e19`.
The loss always returns a scalar and fills an optional `stats` dictionary.
`train/local/effective_clusters_epoch` counts clusters surviving min_cluster_size=4;
it is zero when no cluster survives and the whole-batch fallback is used.
`train/local/configured_clusters_epoch` records requested K,
`train/local/kept_fraction_epoch` records the fraction of samples in surviving clusters,
and `train/local/fallback_epoch` records the fraction of batches using whole-batch fallback.
These names and definitions match Claudio's reporting conventions. Flag B64/K32 as
the planned degenerate cell regardless of whether every batch falls back.

Claudio's table generator also depends on his campaign manifests, run names, and
`<log_root>/train/runs/<run_name>` directory layout. This launcher's run names and
`logs/ablations` layout remain unchanged, so matching metric names alone does not
make these runs automatically discoverable by that generator.

No ramp, reference-method, midpoint or ImageNet-1K runs are submitted by this launcher.
